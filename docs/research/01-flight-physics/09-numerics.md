# 9. วิธีเชิงตัวเลข: ตัวอินทิเกรต ความแข็งของสปริงล้อ และ fixed timestep

> ความเชื่อมั่นโดยรวม: สูง · แหล่งหลัก: ซอร์สโค้ด JSBSim (LGPL-2.1) [N2, N3, N4] · ซอร์สโค้ด FlightGear/YASim และ SimGear [N5, N6, N7] · ECMA-262 [N16] · การคำนวณด้วย Node กับโมเดลจริงของ AirfieldLab [N1, N23]

ข้อตกลงในหัวข้อนี้: ตัวเลขที่มาจากการรันโมเดลปัจจุบันระบุว่า "วัดจากโมเดลปัจจุบัน" และอ้าง [N23] (สคริปต์ `s9_*.mjs` ใน `scripts/`) ตัวเลขที่เป็นการออกแบบหรือการตัดสินใจของผู้วิจัยระบุว่า "ค่าประมาณ" พร้อมวิธีได้มา ค่าคงที่ทางคณิตศาสตร์ที่คำนวณได้แน่นอน (เช่นขอบเสถียรของ RK4) ไม่ใช่ค่าประมาณ แต่ก็อ้างสคริปต์ที่ใช้คำนวณ

## 9.0 สรุปสั้น
- RK4 ที่ 240 Hz ของโมเดลปัจจุบัน**เสถียรและแม่นพอแล้ว** ค่าลักษณะเฉพาะ (eigenvalue) ที่เร็วที่สุดของโหมดอากาศพลศาสตร์มี |λ|·Δt ไม่เกิน 0.04 ส่วนโหมดที่เร็วที่สุดจริงมาจาก**แรงเสียดทาน tanh ของล้อ** ไม่ใช่สปริงสตรัท โหมดนี้มี |λ|·Δt = 0.25 ตอนจอดนิ่ง และ 0.74 ที่จุดโหลดสูงสุดของการแตะพื้นแรง 5 m/s เทียบกับขอบเสถียร 2.785 จึงยังเสถียรอยู่ ข้อผิดพลาดจริงที่ 240 Hz เป็น**อันดับหนึ่ง** (ประมาณ 4.6 cm หลังบิน 10 s) และมาจากการอัปเดตแอคชูเอเตอร์ ตัวกรอง α̇ และลมแบบทีละก้าว ไม่ได้มาจาก RK4 จึง**ไม่ควรเปลี่ยนตัวอินทิเกรต** [N23]
- ข้อบกพร่องเชิงฟิสิกส์ที่วัดได้ชัดที่สุดคือแรงเสียดทาน `tanh` **จับล้อให้หยุดนิ่งไม่ได้** เมื่อเหยียบเบรกเต็มที่ เครื่องยังไหลไปที่ 0.0119 m/s (43 m/h) ภายใต้แรงขับ idle 518 N แนะนำให้ใช้แบบจำลองสปริงขนแปรง (bristle) ต่อล้อ แล้วอัปเดตสถานะด้วยสูตรเอ็กซ์โปเนนเชียลแบบแม่นตรงหลังแต่ละก้าว (แนวคิดเดียวกับ "stuck point" ของ YASim [N5]) ต้นแบบที่ทดลองหยุดการไหลได้ (< 0.1 mm ใน 50 s) เสถียรถึง Δt = 1/30 s และใช้เวลาเพิ่ม 0.5–1.2 µs ต่อก้าว (วัดสองรอบ ได้ 6.40 และ 7.05 µs เทียบกับ 5.86 µs)
- ลูปเฟรม**ไม่มีการ interpolate สถานะตอนเรนเดอร์** และตัวสะสมเวลา (accumulator) มีปัญหาปัดเศษทศนิยม เมื่อป้อน timestamp หน่วย ms ที่ 120 Hz ลงใน `Flight.advance` เฟรม 50% ได้ 1 หรือ 3 ก้าวแทนที่จะเป็น 2 ก้าว ผลคือภาพกระตุก (judder) ราว 96–124 mm RMS ต่อเฟรมที่ 95 kt ซึ่งเท่ากับราว 4.6–6 px ที่ระยะ 24 m ของกล้อง chase ถ้าการเคลื่อนที่ตั้งฉากกับแนวสายตา (ค่าประมาณ ดูหัวข้อ 9.4) แก้ได้ด้วย ε-snap ร่วมกับ lerp/slerp ระหว่างสองสถานะ แนวทางนี้มาจาก Fiedler [N8]
- ผลการบินในความปั่นป่วนเปลี่ยนตาม Δt เพราะ Dryden **สุ่มเลขใหม่ทุกก้าวฟิสิกส์** ระยะแตะพื้นของ autoland ในฉาก xl กระจาย 241–343 m เมื่อเปลี่ยน Δt ถ้าเดินตัวกรองลมด้วยนาฬิกาคงที่ 120 Hz ของมันเอง ระยะจะลู่เข้าเหลือ 240.3–240.8 m ทุก Δt
- งบประมาณเวลาเหลือมาก: `Flight.tick` ใช้ 5.1 µs ต่อครั้ง (Node 22; รันซ้ำตอนตรวจทานได้ 4.5 µs) ที่ 240 Hz คิดเป็นราว 0.11–0.12% ของหนึ่งคอร์ จึงไม่ต้องใช้ Web Worker หรือ SharedArrayBuffer การส่งข้อความไป-กลับระหว่าง worker ใน Node ใช้เวลา 36 µs ซึ่งแพงกว่าฟิสิกส์ทั้งก้าว และ GitHub Pages ตั้ง header COOP/COEP ไม่ได้ [N14]
- เรื่องอื่นที่ควรแก้: `qToEuler` คืนค่าผิดที่ θ = ±90° พอดี (เมทริกซ์ที่สร้างกลับคลาดถึง 0.45 และ 1.3) ไม่ได้หยุดซิมอัตโนมัติเมื่อแท็บถูกซ่อน และยังไม่มีชุดทดสอบเชิงตัวเลข (ไม่มี `test/numerics.test.mjs` และ CI รันเฉพาะ geo กับ runways)

## 9.1 สภาพปัจจุบันใน AirfieldLab
**ตัวอินทิเกรต** `Aircraft.step` (src/20-flight.js:253–270) ใช้ RK4 คลาสสิกกับเวกเตอร์สถานะ 13 ตัว `[n e d | vn ve vd | qw qx qy qz | p q r]` แล้วทำให้ควอเทอร์เนียนมีขนาด 1 ทุกก้าว (บรรทัด 266–267) ใน `step` ยังมีส่วนที่**อยู่นอก RK4** และอัปเดตก้าวละครั้งด้วยวิธีอันดับหนึ่ง ได้แก่ (1) `wind.update` ซึ่งสุ่ม Gaussian ใหม่ทุกก้าว (บรรทัด 86) (2) `actuators(dt)` ซึ่งจำกัดอัตราของพื้นผิวบังคับและหน่วงคันเร่งแบบ exponential แม่นตรง (บรรทัด 241–251) (3) α̇ จากผลต่างจำกัดกับตัวกรอง `Math.min(1, dt/0.05)` ซึ่งเป็น Euler ไม่ใช่ exponential (บรรทัด 275) ในแต่ละก้าวมีการเรียก `deriv` 5 ครั้ง คือ 4 ครั้งใน RK4 และอีก 1 ครั้งใน `updateAir` และ `updateAir` สร้างอาร์เรย์และอ็อบเจ็กต์ใหม่ทุกก้าว [N1]

**ล้อ** (บรรทัด 203–225): สตรัทเป็นสปริง-แดมเปอร์เชิงเส้น $N=\max(0,\,k\min(\delta,s)+12k\max(0,\delta-s)+c\,\dot\delta)$ มี `k` 5.2e4/1.25e5 N/m, `c` 5.0e3/1.25e4 N·s/m และระยะยุบ 0.22/0.25 m (หัว/หลัก) แรงเสียดทานเป็น `−N·μ·tanh(v/0.25)` ตามแนวล้อ และ `−N·0.65·tanh(v/0.35)` ด้านข้าง ใช้ μ = 0.022 + 0.55·brake

**ลูปเวลา**: `Flight.advance` (บรรทัด 612–616) เป็น accumulator ที่ Δt = 1/240 s จำกัด `realDt` ไว้ที่ 0.1 s และไม่เกิน 60 ก้าวต่อเฟรม เนื่องจาก 0.1 s × 240 = 24 ก้าว เพดาน 60 จึงไม่มีวันถึง `frame()` ใน src/90-app.js:444–460 จำกัด dt ที่ 0.1 s อีกชั้นหนึ่ง แล้วเรียก `fl.advance(dt * warp)` (warp เป็น 1, 2 หรือ 0 = หยุด) ส่วน `poseFrom` (90-app.js:372) วาดเครื่องบินจาก `ac.x` ล่าสุด**โดยไม่ interpolate** ไม่มีตัวฟัง `visibilitychange` มีเพียง `blur` ที่ล้างปุ่มที่กดค้าง (90-app.js:344) อินพุตอ่านเฟรมละครั้ง (`readInputs`, 90-app.js:359) แล้วใช้ค่าเดิมกับทุก tick ในเฟรมนั้น ข้อสังเกต: `readInputs` ใช้คีย์บอร์ดแบบไล่ค่าขึ้นลง (ramp 2.0–5.0 ต่อวินาที) อยู่แล้ว ไม่ได้เป็น "binary" ตามที่ CLAUDE.md เขียน

**การเล่นซ้ำ**: `Recorder` บันทึก**สถานะ** 10 Hz (บรรทัด 547–571) แล้ว interpolate ตำแหน่งแบบ lerp และควอเทอร์เนียนแบบ nlerp โดยเลือกซีกที่สั้นกว่า RNG เป็น mulberry32 (บรรทัด 64–68)

## 9.2 ตัวอินทิเกรต: ทางเลือก ความเสถียร และสิ่งที่ JSBSim/FlightGear ใช้
**สมการที่อินทิเกรต** มีรูปทั่วไปดังนี้

$$\dot{\mathbf x}=\mathbf f(\mathbf x,\mathbf u,t),\qquad \mathbf x=[\mathbf p^{N},\ \mathbf v^{N},\ \mathbf q,\ \boldsymbol\omega^{B}]$$

โดย $\mathbf p^N$ คือตำแหน่ง NED (m) จาก ARP ($d$ ชี้ลง), $\mathbf v^N$ คือความเร็ว NED (m/s), $\mathbf q=[q_w,q_x,q_y,q_z]$ คือควอเทอร์เนียนที่หมุนจาก body ไป NED (ไร้หน่วย, $|\mathbf q|=1$), $\boldsymbol\omega^B=[p,q,r]$ คืออัตราหมุนในแกน body FRD (rad/s) และ $\mathbf u$ คือตำแหน่งพื้นผิวบังคับ คันเร่ง และเบรก

**ความเสถียรเชิงเส้น**: ถ้าระบบเชิงเส้นรอบจุดทำงานมีค่าลักษณะเฉพาะ $\lambda$ (s⁻¹) วิธี Runge–Kutta ชัดแจ้งจะคูณโหมดนั้นด้วย $R(z)$ ทุกก้าว เมื่อ $z=\lambda\Delta t$

$$R_{\rm Euler}=1+z,\quad R_{\rm RK2}=1+z+\tfrac{z^2}{2},\quad R_{\rm RK4}=1+z+\tfrac{z^2}{2}+\tfrac{z^3}{6}+\tfrac{z^4}{24}$$

โหมดจะไม่โตก็ต่อเมื่อ $|R(z)|\le 1$ ขอบที่คำนวณได้มีดังนี้ RK4 ถึง $z=-2.7853$ บนแกนจริง และ $|z|=2.8284$ ($2\sqrt2$) บนแกนจินตภาพ Euler และ RK2 ถึง $-2$ บนแกนจริง แต่ไม่เสถียรบนแกนจินตภาพ (ค่าเท่ากับ 0) [N23, s9_stability_regions.mjs] สำหรับออสซิลเลเตอร์ไม่มีแดมปิง semi-implicit (symplectic) Euler และ Störmer–Verlet เสถียรเมื่อ $\omega\Delta t<2$ [N20] ส่วนความแม่นต่อก้าวของ RK4 วัดเป็นความคลาดสัมพัทธ์ $|R(z)-e^{z}|/e^{z}$ ได้ 9.1e-8 ที่ $z=-0.1$, 1.0e-5 ที่ $-0.25$, 4.0e-4 ที่ $-0.5$, 3.4e-3 ที่ $-0.74$ และ 1.9e-2 ที่ $-1$ [N23]

## 9.3 ความแข็งของการสัมผัสพื้น: สตรัท แรงเสียดทาน sub-stepping และ stick-slip
**ฟิสิกส์ของสตรัท** แต่ละสตรัทเมื่อมองเป็นระบบหนึ่งองศาอิสระ (ใช้มวลที่ลงบนล้อนั้น $m_i=N_i/g$) มีค่า

$$\omega_n=\sqrt{k/m},\qquad \zeta=\frac{c}{2\sqrt{k\,m}}$$

โดย $k$ คือความแข็งสปริง (N/m), $c$ คือสัมประสิทธิ์แดมปิง (N·s/m) และ $m$ คือมวลประสิทธิผล (kg) หรือโมเมนต์ความเฉื่อย (kg·m²) สำหรับโหมดหมุน โหลดสถิตย์ที่วัดได้คือ 3193/9436/9436 N (หัว 14.5%, หลักข้างละ 42.8%) สตรัทยุบสถิตย์ 0.061 m จากระยะ 0.22 m (หัว) และ 0.076 m จาก 0.25 m (หลัก) [N23, s9_gear_numbers.mjs]

|---|---|---|---|---|
| สตรัทหัว (325.6 kg) | 12.6 | 2.01 | 0.61 | 208 / 168 / 96 / 89 |
| สตรัทหลัก (962.2 kg) | 11.4 | 1.81 | 0.57 | 230 / 183 / 100 / 102 |
| heave ทั้งลำ (2250 kg) | 11.6 | 1.84 | 0.575 | 226 / 180 / 99 / 100 |
| roll บนล้อหลัก (Ixx 2600) | 15.2 | 2.42 | 0.76 | 181 / 145 / 100 / 65 |
| สตรัทหลักยุบสุด (13k) | 41.1 | 6.54 | 0.16 | 72 / 31 / 7.7 / 42 |
| roll เมื่อยุบสุดทั้งสองข้าง | 54.8 | 8.72 | 0.21 | 54 / 26 / 7.7 / 30 |

ค่า heave ในตารางตรงกับค่าลักษณะเฉพาะจาก Jacobian (−6.69±9.48i คือ ω = 11.6, ζ = 0.577) จะเห็นว่า**สตรัทไม่ใช่ตัวที่แข็ง** ที่ 240 Hz (4.17 ms) มีระยะเผื่อมากกว่า 10 เท่า แม้ตอนยุบสุด

**แรงเสียดทาน tanh คือตัวที่แข็งจริง** แรงตามแนวล้อของแต่ละล้อคือ

$$F_\ell=-\mu N\tanh\!\left(\frac{v_\ell}{v_0}\right),\qquad c_{\rm eff}=\left.\frac{\partial F_\ell}{\partial v_\ell}\right|_{v=0}=\frac{\mu N}{v_0}$$

โดย $v_\ell$ คือความเร็วของจุดสัมผัสตามแนวล้อ (m/s), $v_0$ คือความเร็วอ้างอิงที่ทำให้แรงอ่อนตัวลง (0.25 m/s ตามแนวล้อ และ 0.35 m/s ด้านข้างในโค้ดปัจจุบัน) และ $\mu$ คือสัมประสิทธิ์ (ไร้หน่วย) เมื่อแทนค่าโหลดสถิตย์จะได้ $c_{\rm eff}$ ตามแนวล้อขณะเบรกเต็ม 43,460 N·s/m ($\tau=m/c$ = 51.8 ms) ไม่เบรก 1,942 N·s/m ($\tau$ = 1.16 s) และด้านข้าง 40,980 N·s/m ($\tau$ = 54.9 ms) แรงด้านข้างกระทำที่จุดสัมผัสซึ่งอยู่ต่ำกว่า CG ราว 1.30 m (ตำแหน่งล้อ `g.b[2]` = 1.38 m ลบระยะยุบสถิตย์ 0.076 m ตามแขนโมเมนต์ `arm` ในโค้ด) จึงคู่กับการหมุน roll เป็นโหมดที่เร็วที่สุด λ = −60 s⁻¹ ($\tau$ = 16.6 ms) [N23]

**ผลเสียของ tanh: จับนิ่งไม่ได้** ภายใต้แรงคงที่ $T$ ระบบจะเข้าสู่ความเร็วคงที่ที่

$$v_c=v_0\,\operatorname{artanh}\!\left(\frac{T}{\sum_i \mu_i N_i}\right)$$

แทนค่า $T$ = 518 N (idle 4.5% ของ 11.5 kN) และ $\sum\mu N$ = 10,866 N ได้ $v_c$ = 0.0119 m/s ตรงกับที่วัดได้ 0.0119 m/s (ไหล 0.718 m ใน 60 s) [N23] ถ้าใช้แรงขับสถิตย์เต็ม 11.5 kN ซึ่งมากกว่า 10.9 kN เครื่องจะไถลทั้งที่เบรกอยู่ (ประเด็นนี้เป็นเรื่องของหัวข้อเครื่องยนต์และเบรก) การลด $v_0$ จะลดการไหล แต่ $c_{\rm eff}$ ก็จะเพิ่ม ทำให้ |λ| โตตาม ผลวัดจาก Jacobian ตอนจอด (s9rev_v0scale.mjs) [N23]: ลด $v_0$ ตามแนวล้อเป็น 0.025 m/s (ด้านข้างคง 0.35) ได้ |λ| สูงสุด 301 s⁻¹ (|λ|Δt = 1.25 ที่ 240 Hz) แต่การไหลลดเพียง 10 เท่าเหลือ 1.2e-3 m/s และถ้าลดทั้งสองแกน 10 เท่า (0.025/0.035 m/s) ได้ 479 s⁻¹ (|λ|Δt = 2.0) ซึ่งเข้าใกล้ขอบ 2.785 ตั้งแต่ตอนจอด ก่อนจะมีโหลดล้อเพิ่มตอนแตะพื้น (ฉบับก่อนตรวจทานประมาณจากสเกล λ ∝ 1/v₀ ไว้ที่ 600 s⁻¹ ซึ่งสูงเกินจริง)

**การทดลองกวาด Δt** (s9_dtsweep.mjs, s9_dtsweep2.mjs) [N23]
- จอดนิ่ง 6 s ได้ h = 1.30372 m และ Σโหลด/W = 1.000 ทุก Δt ตั้งแต่ 1/30 ถึง 1/4000 s

- ตกลงพื้นแบบสมมาตร (45 m/s, θ 5°, idle) ที่ 1, 2, 5 m/s ไม่ระเบิดทุก Δt จนถึง 1/30 s ที่ 5 m/s และ 240 Hz โหลดสูงสุด 57,871 N เทียบกับ 58,175 N ที่ 4 kHz (−0.5%) และ nz สูงสุด 6.75 เทียบกับ 6.82 (−1.0%) ที่ 60 Hz ได้ 58,557 N และ 6.65

**ต้นแบบที่ทดลองแล้ว (เฉพาะใน scripts/ ไม่ได้แก้ repo)**
- *ต้นแบบ A* ใส่สถานะ bristle $\dot z=v\,(1-\operatorname{sgn}(v)\,z/z_0)$ ลงใน RK4 ตรง ๆ ผลคือจอดนิ่งได้ แต่การเบรกจาก 15 m/s ที่ 240 Hz ให้ระยะหยุด −9.3 m (ผิดทิศทาง) ขณะที่ 2 kHz ได้ 31.9 m สาเหตุคือ $\lambda=-|v|/z_0=-3000$ s⁻¹ ทำให้ $|\lambda|\Delta t=12.5$ ดังนั้นถ้าอินทิเกรตแบบชัดแจ้ง ต้องมี $|v|<2.785\,z_0/\Delta t=3.3$ m/s ที่ 240 Hz จึงใช้ไม่ได้ (s9_bristle_test.mjs) [N23]
- *ต้นแบบ B (แนะนำ)* ให้ z คงที่ระหว่าง stage ของ RK4 แล้วเดินหน้าหลังจบก้าวด้วยคำตอบแม่นตรงเมื่อ v คงที่ วิธีนี้เป็น exponential integrator ที่เสถียรทุก Δt

$$z_{n+1}=s\,z_0+(z_n-s\,z_0)\,e^{-|v|\Delta t/z_0},\qquad s=\operatorname{sgn}(v)$$

$$F=-\mu N\;\operatorname{clamp}\!\left(\frac{z+\tau v}{z_0},-1,1\right)$$

  โดย $z$ คือการโก่งของขนแปรง (m) ซึ่งมีทั้งตามแนวล้อและด้านข้าง, $z_0$ = 0.005 m คือระยะโก่งที่แรงถึง μN (ค่าเดียวกับค่าเริ่มต้นของ YASim [N5]) และ $\tau$ = 0.02 s คือค่าคงตัวแดมปิง (ค่าประมาณ: เลือกให้ความชัน $\mu N\tau/z_0=4\,\mu N$ s/m เท่ากับความชันของ tanh ตามแนวล้อ $\mu N/0.25$ แกนตามแนวล้อจึงไม่แข็งขึ้น ส่วนด้านข้างชันกว่า tanh เดิม $\mu N/0.35$ ราว 1.4 เท่า แต่ผลทดลองยังเสถียรถึง Δt = 1/30 s) แกนตามแนวล้อใช้ μ = 0.55·brake ร่วมกับแรงต้านการหมุน tanh เดิม (0.022) เพราะล้อที่หมุนอิสระไม่ควรติดพื้น ส่วนด้านข้างใช้ μ = 0.65 ผลที่ได้ (s9_bristle2_test.mjs) [N23]:

**Sub-stepping และ multirate**: Macklin และคณะแสดงว่าการแบ่งเป็นหลายก้าวย่อยแต่ละก้าววนซ้ำครั้งเดียวมีประสิทธิภาพกว่าก้าวใหญ่ที่วนซ้ำหลายครั้ง ทั้งในแง่ความเสถียรและการหน่วงเทียม [N19] สำหรับ AirfieldLab ตอนนี้ยังไม่จำเป็น เพราะ |λ|Δt ≤ 0.74 ที่ 240 Hz และการเพิ่ม rate ทั้งระบบเป็น 480 Hz มีต้นทุนเพียง 2.5 ms ต่อวินาทีจริง ง่ายกว่าแยก multirate (เช่นล้อ 960 Hz ขณะอากาศ 240 Hz) ซึ่งต้องจัดการการแช่แรงอากาศและการเชื่อมสถานะ เกณฑ์ที่แนะนำ (ค่าประมาณ จากตารางความคลาดต่อก้าวในหัวข้อ 9.2): ถ้าโมเดลล้อในอนาคตทำให้ max|λ|Δt > 0.75 ในกรณีทดสอบ T-N-05 ให้เพิ่ม `physicsHz` เป็น 480 ก่อน ส่วน multirate ค่อยพิจารณาเมื่อ 480 Hz ยังไม่พอ ถ้าเพิ่มสปริงยางต่ออนุกรมกับสตรัท ให้เขียนแบบไร้มวล (เชิงพีชคณิต) แทนการเพิ่มมวลใต้สปริงเป็นสถานะใหม่ เพราะมวลใต้สปริงที่เบามากจะสร้างโหมดความถี่สูง (เป็นการตัดสินใจเชิงออกแบบ ยังไม่ได้วัด)

**การกระแทกตอนแตะพื้นและการยุบสุด**: แดมเปอร์เชิงเส้นสร้างแรง $c\,v$ ทันทีที่ล้อแตะ JSBSim จำกัด |ความเร็วยุบ| ไม่ให้เกิน `compressLength/dt` (โค้ดตรวจทุกก้าวนอกช่วง trim แต่คอมเมนต์ระบุว่ามีไว้สำหรับก้าวที่ล้อเพิ่งเริ่มสัมผัส ซึ่งเป็นกรณีเดียวที่ขีดนี้มีผลจริง; FGLGear.cpp บรรทัด 366–378) [N3] เมื่อทดลองกับการตก 5 m/s ผลแทบไม่ต่าง (nz สูงสุด 6.82 ทั้งสองแบบที่ 4 kHz และ 6.75 เทียบกับ 6.82 ที่ 240 Hz; s9_dampclamp.mjs) [N23] แสดงว่า nz ที่สูงเกิดจากค่า $c$ ตลอดช่วงยุบ ไม่ได้เกิดจากเชิงตัวเลข การปรับให้ใกล้ oleo จริง (แดมปิงแปรตาม $v|v|$ และสปริงอากาศ) เป็นงานของหัวข้อล้อ ในด้านตัวเลข โซนยุบสุด 13k ยังเสถียรที่ 240 Hz (Δt สูงสุดของ RK4 อยู่ที่ 54 ms)

## 9.4 Fixed timestep ที่แยกจากการเรนเดอร์
**รูปแบบ accumulator** ของ Fiedler [N8] คือรับเวลาเฟรม จำกัดไม่ให้เกินค่าหนึ่ง (บทความใช้ 0.25 s) แล้วเดินฟิสิกส์ด้วย Δt คงที่จนเวลาที่สะสมไว้ไม่พอหนึ่งก้าว จากนั้นวาดสถานะที่ผสมระหว่างก้าวก่อนหน้ากับก้าวปัจจุบันด้วย $\alpha=a/h$ บทความระบุว่าถ้าไม่ interpolate ภาพจะแสดงสถานะ ณ เวลาที่ต่างจากเวลาเรนเดอร์ และทำให้เกิด "subtle but visually unpleasant stuttering" [N8] SimGear ของ FlightGear ใช้แนวคิดเดียวกันแต่ปัดเศษจำนวนก้าวด้วย `roundToInt` [N7] เขียนเป็นสมการได้ดังนี้

$$a\leftarrow a+\min(\Delta t_{\rm frame},T_{\max});\quad \text{while }(a\ge h-\varepsilon \wedge n<n_{\max})\{\ \mathbf x_{\rm prev}\leftarrow\mathbf x;\ \mathbf x\leftarrow\Phi_h(\mathbf x);\ a\leftarrow a-h\ \}$$

$$\alpha=\operatorname{clamp}(a/h,0,1),\qquad \mathbf p_r=(1-\alpha)\,\mathbf p_{\rm prev}+\alpha\,\mathbf p,\qquad \mathbf q_r=\operatorname{slerp}(\mathbf q_{\rm prev},\mathbf q,\alpha)$$

โดย $h$ = 1/240 s คือก้าวฟิสิกส์, $a$ คือเวลาที่สะสมไว้ (s), $T_{\max}$ = 0.1 s, $n_{\max}=\lceil T_{\max}/h\rceil$ = 24, $\varepsilon$ = 1e-9 s (ค่าประมาณ: เล็กกว่า $h$ ราว 4×10⁶ เท่า แต่ใหญ่กว่าความคลาดปัดเศษของ $a$ ซึ่งอยู่ที่ระดับ 1e-16 ถึง 1e-15 s), $\Phi_h$ คือ `tick`, และ $\mathbf p_r,\mathbf q_r$ คือตำแหน่งและควอเทอร์เนียนที่ใช้วาด ภาพจะช้ากว่าฟิสิกส์คงที่ $h$ = 4.17 ms

**ผลวัดปัญหาปัจจุบัน** (s9_advance.mjs ใช้ `Flight.advance` จริงกับ timestamp หน่วย ms แบบเดียวกับ `frame()`) [N23]: ที่ 60 Hz ได้ 3/4/5 ก้าว = 64/1872/64 เฟรม ที่ 120 Hz ได้ 1/2/3 ก้าว = 506/988/506 เฟรม และที่ 144 Hz ได้ 1/2 ก้าว = 667/1333 ตามที่ควรเป็น เวลาจำลองรวมยังตรงกับเวลาจริง แต่การเคลื่อนที่ต่อเฟรมไม่สม่ำเสมอ สาเหตุคือ `now − last` ที่คำนวณเป็นทศนิยมทำให้ `acc` ต่ำกว่า `dt` เพียงระดับ ulp ของเลขทศนิยม เมื่อเติม ε = 1e-9 แล้ว 120 Hz ได้ 2 ก้าวทุกเฟรม และ 240 Hz ได้ 1 ก้าวทุกเฟรม (s9_judder_hist.mjs)

ขนาดของการกระตุกเมื่อเทียบกับการเคลื่อนที่ในอุดมคติ $V/f$ ที่ $V$ = 95 kt (s9_judder.mjs จำลองด้วย Node) [N23]:

|---|---|---|
| 60 Hz (timestamp ตรงพอดี) | 0 / 0 | – |
| 60 Hz (สั่น ±0.5 ms) | 145 / 204 | 20 / 48 |
| 75 Hz | 82 / 163 | 20 / 48 |
| 120 Hz | 124 / 204 | 20 / 48 |

เมื่อ interpolate ความคลาดที่เหลือเท่ากับการสั่นของ timestamp ที่ใส่เข้าไปเองในการจำลอง ถ้ากล้อง chase อยู่ห่าง 24 m ภาพสูง 1080 px และ FOV แนวตั้ง 50° (ค่าใน 90-app.js) แบบ pinhole ที่กลางภาพจะได้ 1 mm ≈ 540/tan 25° ÷ 24 000 = 0.048 px ดังนั้น 96 mm ≈ 4.6 px และ 124 mm ≈ 6 px (ค่าประมาณ; s9_judder.mjs พิมพ์ 0.052 px/mm เพราะใช้การประมาณมุมแบบเชิงเส้น FOV/1080 ซึ่งสูงไป 7%) ตัวเลขนี้เป็นขอบบนสำหรับการเคลื่อนที่ที่ตั้งฉากกับแนวสายตา กล้อง chase อยู่ด้านหลังเครื่อง การเคลื่อนที่ตามแนวบินจึงอยู่ในแนวสายตาเป็นส่วนใหญ่ การกระตุกจะเห็นชัดที่พื้นและวัตถุที่เลื่อนผ่านด้านข้างภาพมากกว่าที่ตัวเครื่อง MDN ระบุว่า rAF เรียกตามอัตรารีเฟรชของจอ โดย "60hz … though 75hz, 120hz, and 144hz are also widely used" และเตือนให้ใช้ timestamp ที่ได้รับมามิฉะนั้นแอนิเมชันจะเร็วขึ้นบนจอรีเฟรชสูง [N9]

**Spiral of death**: Fiedler อธิบายว่าเมื่อซิมตามเวลาจริงไม่ทัน ก้าวที่ต้องไล่ตามจะยิ่งทำให้ช้าลง ทางแก้คือจำกัดจำนวนก้าวต่อเฟรมและยอมให้ซิมช้าลงชั่วคราว [N8] ของเราใช้ 5.1 µs × 24 = 0.12 ms ต่อเฟรมในกรณีแย่สุด จึงเกิดปัญหานี้ได้ยากมาก แนะนำให้ (1) ตั้ง `maxSteps = Math.ceil(0.1/dt)` แทนเลข 60 ที่ไม่มีผล และ (2) เมื่อชนเพดานให้ทิ้งเวลาที่ค้าง (`acc = Math.min(acc, dt)`) แทนการยกยอดไปเฟรมถัดไป

**แท็บพื้นหลังและการหยุดชั่วคราว**: MDN ระบุว่า rAF "paused in most browsers when running in background tabs or hidden `<iframe>`s" [N9] บทความของ Chrome ระบุว่า rAF "will wait for the page to be visible" และตัวจับเวลาที่ต่อกันเป็นสาย (chained) ถูกจำกัดเป็นสามระดับ ได้แก่ ไม่จำกัดเมื่อหน้าเห็นอยู่ ตรวจทุก 1 s เมื่อซ่อน และตรวจทุก 1 นาทีเมื่อซ่อนเกิน 5 นาที chain count ≥ 5 และเงียบอย่างน้อย 30 s [N11] MDN Page Visibility API ระบุว่าการจำกัดตัวจับเวลาเป็นแบบ budget และใน Chrome เริ่มหลังซ่อน 10 s [N10] ผลต่อ AirfieldLab คือห้ามเดินฟิสิกส์ด้วย `setTimeout`/`setInterval` และควรคงการขับด้วย rAF ไว้ ตอนนี้เมื่อกลับมาที่แท็บ เฟรมแรกถูกจำกัดที่ 0.1 s ซิมจึงเดินต่อแค่ 0.1 s (`advance(30)` ให้ 24 ก้าว = 0.1000 s) ซึ่งปลอดภัย แต่ผู้ใช้กลับมาเจอเครื่องบินที่บินต่ออยู่ทันที แนะนำให้ฟัง `visibilitychange` เมื่อ `document.hidden` ให้ตั้ง `warp = 0` ล้างปุ่มที่กดค้างและคันบังคับสัมผัส และแสดงข้อความภาษาไทยว่า "หยุดชั่วคราว — กด P เพื่อบินต่อ" [N10]

**Web Worker และ SharedArrayBuffer**: การใช้ SharedArrayBuffer ต้องเป็น secure context และ cross-origin isolated มิฉะนั้น `postMessage()` จะ throw [N12] และ cross-origin isolated ต้องมี header `Cross-Origin-Opener-Policy: same-origin` คู่กับ `Cross-Origin-Embedder-Policy: require-corp` หรือ `credentialless` [N13] GitHub Pages ตั้ง header เองไม่ได้ คำขอ community discussion #13309 (เปิด 23 มี.ค. 2022) ยังไม่มีฟีเจอร์นี้และยังมีสถานะ "Unanswered" ความเห็นเมื่อ 10 ก.ค. 2023 เขียนในนามผู้ให้บริการว่า "This is a scenario we would support with custom headers. No ETA at the moment" (หน้าเว็บไม่ได้ติดป้ายว่าผู้เขียนเป็นพนักงาน GitHub) และผู้ใช้ยังขอฟีเจอร์นี้อยู่จนถึงความเห็นล่าสุดเมื่อ 25 ต.ค. 2026 [N14] ทางเลี่ยงคือ `coi-serviceworker` (MIT) ซึ่ง "will reload the page on the user's first load" [N15] และมีผู้ใช้รายงานในเธรดเดียวกัน (26 ส.ค. 2025) ว่าทางเลี่ยงนี้ไม่ทำงานแล้วกับ coi-serviceworker v0.1.7 บน Firefox for Windows [N14] ส่วนโฮสต์ artifact ของ claude.ai ยังไม่ได้ตรวจว่าตั้ง header ได้หรือไม่ ผลวัดใน Node (worker_threads) คือข้อความขนาดเล็ก (13 double + อินพุต) ไป-กลับใช้ 36 µs (มัธยฐาน), p99 79 µs และค่าสูงสุด 25 ms (s9_worker_rtt.mjs) [N23] ซึ่งแพงกว่า `tick` ทั้งครั้ง (5 µs) และ worker ยังทำให้ภาพช้าลงอย่างน้อยหนึ่งรอบข้อความเพราะการสื่อสารเป็นแบบ asynchronous **สรุป: ให้ฟิสิกส์อยู่บน main thread** จะพิจารณา worker (ใช้ `postMessage` กับ ArrayBuffer แบบ transferable ไม่ต้องใช้ SAB) ก็ต่อเมื่อฟิสิกส์ใช้เกิน 2 ms ต่อเฟรม ซึ่งคือราว 100 เท่าของปัจจุบัน (ปัจจุบัน 4 tick × 5.1 µs ≈ 0.02 ms ต่อเฟรม 60 Hz; ฉบับก่อนตรวจทานเขียน 400 เท่า ซึ่งเป็นการเทียบกับ tick เดียว)

ที่ 240 Hz ฟิสิกส์ใช้ 1.23 ms ต่อวินาทีจริง (0.12% ของหนึ่งคอร์) หรือ 0.02 ms ต่อเฟรม 60 Hz ถ้าตั้งงบไว้ที่ 2 ms ต่อเฟรม (ค่าประมาณ: ราว 12% ของ 16.7 ms เพื่อให้เหลือเวลาสำหรับ three.js) จะรันได้ราว 390 tick ต่อเฟรม **ส่วนที่จะเพิ่มเข้ามา** (ค่าประมาณจากตาราง): ปีกแบบ 20 strip ใช้ 0.33 µs × 5 deriv ≈ +1.7 µs ต่อก้าว ตารางใบพัดใช้น้อยกว่า 0.1 µs ต่อก้าว ล้อ 4 ก้าวย่อยใช้ราว +2.4 µs ต่อก้าว (ส่วนของล้อใน deriv ≈ 0.6 µs × 4) รวมแล้วราว 9 µs ต่อ tick หรือ 2.2 ms ต่อวินาทีที่ 240 Hz หรือ 0.037 ms ต่อเฟรม 60 Hz ซึ่งยังต่ำกว่างบ 2 ms ราว 54 เท่าบนเครื่องที่วัด และราว 5–11 เท่าบนอุปกรณ์ที่ช้ากว่า 5–10 เท่า (ค่าประมาณ; ตัวคูณความช้า 5–10 เท่า "ยังไม่ยืนยัน" เพราะไม่ได้วัดบนมือถือ ฉบับก่อนตรวจทานเขียนว่าเหลือ 50 เท่าแม้บนอุปกรณ์ช้า ซึ่งผิด) ข้อแนะนำเล็ก ๆ คือ `updateAir` สร้างอาร์เรย์และอ็อบเจ็กต์ใหม่ทุกก้าว ควรใช้บัฟเฟอร์ซ้ำเพื่อลดงานของ GC (P3)

## 9.6 Determinism และการเล่นซ้ำ
**สิ่งที่สเปกรับประกัน**: ECMA-262 ระบุว่า `acos, acosh, asin, asinh, atan, atanh, atan2, cbrt, cos, cosh, exp, expm1, hypot, log, log1p, log2, log10, pow, random, sin, sinh, tan, tanh` "is not precisely specified" และ "recommended (but not specified by this standard)" ให้ใช้ fdlibm [N16] แต่ `Math.sqrt` ต้องคืน 𝔽(√n) ซึ่งคือค่าที่ปัดเศษถูกต้อง และ `Math.imul` นิยามเป็นการคูณจำนวนเต็ม modulo 2³² แบบแม่นตรง [N16] ผลคือ mulberry32 ให้ลำดับเลขเหมือนกันทุกเบราว์เซอร์ แต่ `gauss()` ใช้ `Math.log` และ `Math.cos` ส่วนโมเดลใช้ `exp, pow, tanh, hypot, atan2, asin, sin, cos` จึงไม่รับประกันว่าจะได้ผลตรงกันทุกบิตข้ามเอนจิน

**ผลวัด** (s9_determinism.mjs) [N23]: (1) รันซ้ำบนเอนจินเดียวกันได้สถานะตรงกันทุกบิต (`Object.is` ทั้ง calm และ xl) (2) จำลองเอนจินอื่นโดยรบกวนผลของ `exp, tanh, pow, atan2, sin, cos, log` ทีละ ±1 ulp ผลแตะพื้นของ AP ไม่เปลี่ยนเลย (s, vs, คะแนนเท่าเดิม) และสถานะสุดท้ายต่างกันไม่เกิน 8.5e-12 m (3) รบกวนตำแหน่งเริ่ม 1e-9 m แล้วความต่างหดเหลือ 2.4e-10 m แสดงว่าระบบวงปิดของ AP หดความคลาด ไม่ได้เป็น chaotic ข้อควรระวังคือเงื่อนไขแบบไม่ต่อเนื่อง (`wow`, การสลับโหมด AP, เกณฑ์ crash) ยังอาจพลิกได้ถ้าค่าตกห่างจากเกณฑ์ไม่ถึง 1e-11 ความน่าจะเป็นต่ำมากแต่ไม่เป็นศูนย์

**ความเกี่ยวข้องกับ Δt**: ลำดับลมกระโชกขึ้นกับ Δt เพราะสุ่มหนึ่งครั้งต่อก้าว ฉาก xl ของ AP (seed 5) ให้ระยะแตะพื้น 254.8/240.8/343.2/280.5/306.9 m ที่ Δt = 1/60…1/1000 ส่วนตัวแปร "นาฬิกาลมคงที่ 120 Hz" (เดินตัวกรอง Dryden แบบเดิมทีละ 1/120 s แล้ว lerp ตามเวลาฟิสิกส์) ให้ 240.8/240.8/240.8/240.7/240.3 m และ vs −412…−444 fpm (s9_turbclock.mjs) [N23] จะเห็นว่าความแปรปรวนเดิมมาจากการสุ่มคนละชุด ไม่ได้มาจากความคลาดของการอินทิเกรต ความถี่หักมุมของ Dryden แกน w คือ $V/L_w$ ซึ่งมากสุดราว 49/3.05 ≈ 16 rad/s (2.6 Hz) ที่ h = 10 ft ตามสูตรในโค้ด (ค่าประมาณ: 48.9 m/s ÷ 3.048 m = 16.0 rad/s = 2.55 Hz) นาฬิกา 120 Hz จึงละเอียดกว่าราว 47 เท่า

## 9.7 ควอเทอร์เนียน มุมออยเลอร์ และการห่อมุม
**จลนศาสตร์**: 

$$\dot{\mathbf q}=\tfrac12\,\mathbf q\otimes[0,\ \boldsymbol\omega^B],\qquad \mathbf q_{n+1}=\mathbf q_n\otimes\exp\!\big(\tfrac12[0,\boldsymbol\omega\Delta t]\big)=\mathbf q_n\otimes\Big[\cos\tfrac{\theta}{2},\ \hat{\mathbf n}\sin\tfrac{\theta}{2}\Big],\quad \theta=|\boldsymbol\omega|\Delta t$$

โดย ⊗ คือผลคูณควอเทอร์เนียน, $\hat{\mathbf n}=\boldsymbol\omega/|\boldsymbol\omega|$ และ $\theta$ (rad) คือมุมที่หมุนในหนึ่งก้าว สูตรที่สองคือ "Buss1" ของ JSBSim ซึ่งแม่นตรงเมื่อ ω คงที่ [N2] ผลวัดกับโปรไฟล์ ω(t) ที่ roll ถึง 100°/s นาน 60 s เทียบกับ RK4 ที่ 100 kHz (s9_quat.mjs) [N23]:

| ความถี่ | RK4 + normalize | exp-map ใช้ ω(t) | exp-map ใช้ ω(t+Δt/2) | Euler + normalize | \|q\|−1 ของ RK4 ถ้าไม่ normalize |
|---|---|---|---|---|---|
| 60 Hz | 5.5e-7° | 0.58° | 0.023° | 0.57° | −2.2e-10 |
| 240 Hz | 2.6e-7° | 0.15° | 1.4e-3° | 0.15° | −2.1e-13 |

**ข้อสรุป**: RK4 กับการ normalize ทุกก้าวแบบปัจจุบันดีที่สุดสำหรับเรา ไม่ต้องใช้ Lie-group integrator การ normalize ทุกก้าวแทบไม่มีต้นทุนและป้องกันความคลาดสะสมระยะยาว ใน replay และการวาดให้ใช้ slerp หรือ nlerp ที่เลือกซีกสั้น (`dot < 0` แล้วกลับเครื่องหมาย) แบบที่ `Recorder.at` ทำอยู่ three.js r186 มี `Quaternion.slerpQuaternions(qa, qb, t)` (MIT) ให้ใช้ [N22]

**มุมออยเลอร์ใกล้ θ = ±90°**: `qToEuler` ใช้ `θ = −asin(R31)` และ `φ, ψ` จาก `atan2` ของพจน์ที่เข้าใกล้ศูนย์ ที่ θ = ±90° พอดีจึงได้ φ และ ψ เป็นค่าสุ่มจากความคลาดปัดเศษ (ที่ +90° ได้ φ = 26.57° และ R ที่สร้างกลับคลาด 0.45 ที่ −90° คลาด 1.3) ส่วนที่ 89.9999° ยังถูกต้อง (6.9e-11) นอกจากนี้ `asin` ใกล้ 1 เสียความแม่นของ θ ไปราว 6.7e-11 rad ขณะที่ `atan2` คลาด 0 (s9_euler.mjs) [N23] JSBSim จัดการ gimbal lock โดยตั้ง θ = ±π/2, φ = atan2(−R₂₃, R₂₂) และ ψ = 0 (FGMatrix33.cpp บรรทัด 159–190 เขียนในดัชนีของ R แบบ body→NED ของเรา เพราะ JSBSim เก็บเมทริกซ์ local→body แบบ column-major ตาม FGMatrix33.h) [N4] สำหรับเมทริกซ์ body→NED ของเรา (`R[0..8]` = R11…R33) แนะนำให้ใช้

$$\theta=\operatorname{atan2}\!\big(-R_{31},\sqrt{R_{11}^2+R_{21}^2}\big),\quad \phi=\operatorname{atan2}(R_{32},R_{33}),\quad \psi=\operatorname{atan2}(R_{21},R_{11})$$

และเมื่อ $\sqrt{R_{11}^2+R_{21}^2}<\varepsilon_g$ (gimbal lock; $\varepsilon_g$ = 1e-9) ให้ $\phi=0$ และ $\psi=\operatorname{atan2}(-R_{12},R_{22})$ ซึ่งตรวจแล้วว่าสร้าง R กลับได้คลาด 2e-16 ถึง 4e-16 ที่ ±90° [N23] (ข้อสังเกตจากการตรวจทาน: ที่ θ = 89.9999999° ซึ่ง cos θ ≈ 1.7e-9 ยังมากกว่า $\varepsilon_g$ ทั้งสูตรเดิมและสูตรแนะนำคลาด 2.3e-8 เพราะ atan2 ของพจน์ขนาด 1e-9 เสียความแม่นสัมพัทธ์ ค่านี้ยังเล็กเกินกว่าจะมีผลต่อการวาดหรือ HUD จึงไม่ได้ใส่ใน T-N-13) คำเตือนสำหรับ PilotLaws และ autopilot: ใกล้ ±90° ค่า φ และ ψ ไม่มีความหมาย กฎควบคุมที่จะรองรับการบินผาดแผลงในอนาคตควรใช้เวกเตอร์ (เช่นแกน body ใน NED) แทนมุมออยเลอร์

**การห่อมุม**: `wrapPi` (10-atmo.js) คืนค่าในช่วง [−π, π) โดย `wrapPi(π) = −π` และค่าใหญ่อย่าง 1e9 ยังได้ค่าจำกัด ใช้งานได้ ข้อควรระวังคือห้ามเฉลี่ยหรือ lerp มุมโดยตรง (เช่นฮัดดิงใน `Recorder.at` ซึ่งตอนนี้ lerp ทุกค่าที่เป็นตัวเลข แต่ไม่ได้บันทึก ψ ไว้ จึงยังไม่มีปัญหา) ถ้าต้องผสมมุม ให้ใช้ $\psi_a+\operatorname{wrapPi}(\psi_b-\psi_a)\,u$

**โค้ดแนะนำ (ย่อ) สำหรับ src/20-flight.js**
```js
// Flight: accumulator with ε-snap, explicit step cap, previous state for render interpolation
advance(realDt) {
  const h = this.dt, maxN = Math.ceil(0.1 / h);
  this.acc += Math.min(Math.max(realDt, 0), 0.1);
  let n = 0;
  while (this.acc >= h - 1e-9 && n < maxN) { this.xPrev.set(this.ac.x); this.tick(h); this.acc -= h; n++; }
  if (n === maxN) this.acc = Math.min(this.acc, h);      // drop backlog instead of carrying it
  if (this.acc < 0) this.acc = 0;
  return n;
}
renderPose(out) {               // out: { p: [n,e,d], q: [w,x,y,z] }
  const a = Math.min(1, this.acc / this.dt), A = this.xPrev, B = this.ac.x;
  for (let i = 0; i < 3; i++) out.p[i] = A[i] + (B[i] - A[i]) * a;
  let d = A[6] * B[6] + A[7] * B[7] + A[8] * B[8] + A[9] * B[9], s = d < 0 ? -1 : 1;
  for (let i = 0; i < 4; i++) out.q[i] = A[6 + i] + (s * B[6 + i] - A[6 + i]) * a;   // nlerp (Δθ ≤ 1°/step: error negligible)
  const l = Math.hypot(...out.q); for (let i = 0; i < 4; i++) out.q[i] /= l;
  return out;
}

//   in deriv():  const Fl = -N*0.022*Math.tanh(vl/0.25) - N*mub*clamp((zl + TAU*vl)/Z0, -1, 1);
//                const Fs = -N*0.65*clamp((zs + TAU*vs)/Z0, -1, 1);
//   after step: for each wheel j in contact: s = Math.sign(v); z = s*Z0 + (z - s*Z0)*Math.exp(-Math.abs(v)*dt/Z0); else z = 0
```

## 9.10 ความขัดแย้งของแหล่งข้อมูลและข้อจำกัด
- **อัตราฟิสิกส์**: JSBSim (dT 1/120) [N4] และ FlightGear (model-hz 120) [N6] ใช้ 120 Hz ส่วน AirfieldLab ใช้ 240 Hz สองค่านี้ไม่ได้ขัดกัน เพราะ JSBSim แก้แรงเสียดทานแบบ implicit ด้วย PGS [N3] และ YASim ใช้สปริง stuck point [N5] ส่วนแรงเสียดทาน tanh ของเราต้องใช้ 240 Hz เพื่อให้มีระยะเผื่อ 3.8 เท่าในกรณีแย่สุด
- **Ramp ของแรงเสียดทาน**: YASim ใช้ ramp เชิงเส้นที่ `STOP = 0.1 m/s` [N5] AirfieldLab ใช้ tanh ที่ v₀ = 0.25 และ 0.35 m/s [N1] ค่าทั้งคู่เป็นตัวเลขสำหรับงานตัวเลข ไม่ได้วัดจากล้อจริง
- **Frame clamp**: Fiedler ใช้ 0.25 s [N8] AirfieldLab ใช้ 0.1 s ทั้งสองใช้ได้ 0.1 s ปลอดภัยกว่าสำหรับฟิสิกส์ที่มีการสัมผัสพื้น
- **การนับก้าว**: Fiedler ใช้ `while (acc >= dt)` ซึ่งตัดเศษลง [N8] SimGear ใช้ `roundToInt` จึงยอมให้เศษติดลบได้ [N7] เราแนะนำแบบตัดเศษลงพร้อม ε เพราะเข้ากับ interpolation ได้ตรงกว่า
- **การจำกัดตัวจับเวลาเบื้องหลัง**: บทความ Chrome [N11] (3 ระดับ, 1 s และ 1 นาที) กับ MDN [N10] (budget-based เริ่มหลัง 10 s ใน Chrome) อธิบายคนละกลไก ทั้งคู่ยืนยันว่า rAF ไม่ทำงานเมื่อหน้าถูกซ่อน
- **ชื่อผู้แต่ง NASA TN D-7347**: คอมเมนต์ใน JSBSim เขียน "Bowles" [N2] แคตตาล็อก UNT เขียน "Bowler" [N21]
